## Stack and data inventory

- Next.js **16.2.6**, React **19.2.4**, TypeScript strict, Tailwind 4, pnpm; lockfile resolves Three.js **0.185.1**. No backend/database is required for the game. Save state is localStorage (`runway-save`).
- `GameApp` owns game state and actions; `MapCanvas` owns pointer input, resize, animation and renderer swap; `Scene`/`HitTarget`/`IMapRenderer` connect them.
- `MapOverlay` paints game markers and effects on a separate 2D canvas. `factory.ts` dynamically loads the 3D implementation and can use the 2D renderer.
- `CityRenderer3D.ts` is 968 lines, `cityBuilder.ts` 3,588, `landmarks.ts` 2,175, `uniqueStreet.ts` 1,296, and `test-city-read.ts` 1,474 at this head. These are shared ownership hotspots; parallel edits here are unsafe.
- Offline decode verified **113,569 buildings** (18,406 major / 95,163 minor), **56,793 roads**, **769 parks**, **62 water polygons**, and **9,119 painted facades**. The binary is **6,698,590 bytes**. The existing stats timestamp is 27 August 2026; these are committed snapshot counts, not live London data.
- Bbox: longitude −0.265..0.065, latitude 51.452..51.552. `project()` maps east to +x and south to +y; 3D ground uses `(x, 0, y)`. `METERS_TO_WORLD = 1000 / 111320`.
- Assets: committed OSM binary, landmark GLBs (~9.2 MiB on disk), noticed GLBs (~2.2 MiB on disk). Not all are loaded in every mode. Some hero landmarks and noticed towers are generated procedurally at runtime even when baked files exist.
- External data belongs to `fetch-geodata.ts`, `bake-landmarks.ts`, `bake-noticed.ts`, and related bake helpers. There is no reason to add a runtime AI/geodata service for this scope.

## What this session actually verified

See [the checked evidence](evidence/baseline.md) for command results and captured images. The citystreet view did paint ordinary buildings locally at this head; this is evidence against simply assuming the old crash still occurs everywhere. It also logged React error #418, a hydration mismatch according to [React's official error reference](https://react.dev/errors/418). A successful screenshot does not certify hydration, speed, full-city navigation, or visual fidelity.

## Why this can become a loop — assessment, not proven crash causality

1. Product directions and implementation architectures changed while old “locked” specs stayed discoverable.
2. Local screenshot objections became more special-case geometry, camera presets and exclusions in the same large files.
3. Geometry assertions and deployment checks supplied confidence without proving the player-facing browser result.
4. Detailed landmark work continued while runtime coverage and stability remained unresolved.
5. No repository-visible accepted reference, task-owner ledger or independently reproduced gate kept the work converging.

The recovery response is one product contract, one accepted integration commit at a time, observable browser gates, isolated ownership, and a whole-street approval before wider asset work. A crash's exact CPU/GPU cause still requires profiling; code inspection alone cannot distinguish heap pressure, upload pressure, draw cost, driver failure or other causes.
